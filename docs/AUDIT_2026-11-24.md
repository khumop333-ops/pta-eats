# Roma — UX, Ordering Friction, Performance & Security Audit

**Site:** https://roma.africa · **Date:** 24 November 2026 · **Auditor pass:** full read of `src/`, `supabase/`, migrations, deploy config + live crawl of `/`, `/r`, `/r/magwinya-zone`

**Verdict in one line:** the *money path is genuinely well built* (server-side pricing, no client-trusted totals, verified Yoco webhook, scoped RLS). The risk is not price tampering — it is **abuse and friction**: anyone can create unlimited orders with a 5-character "phone number", the app has **zero rate limiting or bot protection**, and the mobile experience carries a 611 kB JS bundle plus a render-blocking Google Fonts chain.

- ✅ **Deliverer access is scoped to `deliverer_id = auth.uid()`**, and CI asserts the scoped policies exist (`.github/workflows/supabase-ci.yml`).
- ✅ **No XSS sink in the storefront.** No `dangerouslySetInnerHTML` on user content (only shadcn's `chart.tsx`); the alert email escapes HTML with `escapeHtml()`; the receipt PNG uses canvas `fillText`. Delivery notes/addresses are safe today.

## 3. Critical Flow Breakdown — Menu Browsing → Checkout → Payment

**Step 1 — Landing (`/`)**
`Index` → `HeroSection` (search) + `CampaignBanner` + `FeaturedRestaurants`. Restaurants come from `useHomepageRestaurants` → React Query, 5-min cache, one request shared between hero and grid.
✅ *Hardened:* no client pricing, no auth required, good caching.
⚠️ *Gap:* hero `public/hero-food.jpg` is **398 kB** and is the LCP element.

**Step 2 — Directory (`/r`) and restaurant page (`/r/:slug`)**
`PublicRestaurantPage` fetches `restaurants` by `slug` then `menu_items` by `restaurant_id` ordered by `sort_order`.
✅ *Hardened:* `StorefrontImage` lazy-loads every non-hero image and falls back to a branded mark instead of a broken `<img>`; real empty/error/retry states exist (not blank screens).
⚠️ *Gaps:* no `is_listed` filter, no `is_available` flag, identical `4` rating and `30-40 min` ETA for all restaurants, single `Add` button.

**Step 3 — Cart**
`CartContext` persists to `localStorage` (`roma-cart-v1`) with a **24 h TTL**, re-validates every stored item (`isCartItem`) and **discards a mixed-restaurant cart** rather than silently merging. Delivery fee is read from the restaurant row with a Magwinya Zone override.
✅ *Hardened:* the stored price is *display-only* — the server re-prices. The code comment says so explicitly and the RPC confirms it.
⚠️ *Gap:* the fee shown is a client-side preview; it can drift from the server value if the admin changes `delivery_fee` mid-session. Consider showing "final total confirmed at checkout".

**Step 4 — Checkout (`/order`)**
`WhatsAppCheckout` collects name / phone / address / notes, then calls `placeDirectLockedOrder`.
⚠️ *This is the weakest link in the whole funnel:* **no auth, no CAPTCHA, no rate limit, phone validated by length only, address validated by length only.**
If the Edge Function is unreachable, `directOrder.ts` falls back to calling the `place_storefront_order` RPC directly — pricing stays server-side, so the fallback is *safe*, just less observable.

**Step 5 — Server pricing (the strong part)**
`place_storefront_order` (migration `20261124170000`) does, in order:
1. `btrim` + length-check name (1–120), phone (5–30), address (5–300), notes (≤500)
2. validate each item is a UUID and quantity is an integer 1–50
3. **require every requested item to still exist** (`v_matched_count <> v_distinct_requested` → reject)
4. **require all items to resolve to exactly one `restaurant_id`**
5. compute subtotal from `menu_items.price` — never from the request
6. compute the fee from `restaurants.delivery_fee` with the Magwinya fallback
7. apply the free-delivery credit only for a signed-in user, inside the same transaction
8. set `is_preorder` from the **server's** SAST hour (08:00–18:00), not the browser clock
9. insert the order with `payment_status='pending'`, `payment_method='eft_or_cash'`, a fresh `order_number` and a fresh `receipt_token`
10. return `get_order_receipt(token)`

✅ This is a genuinely well-designed function. **The only thing missing is a rate limit around it.**

**Step 6 — Payment**
- **Live path:** bank transfer (EFT) or cash on delivery. The order is created as `pending`; the customer is given the account details and a shareable locked receipt PNG.
- **Card path (dormant):** `create-yoco-payment` authenticates the caller, checks `order.user_id === user.id`, refuses already-paid orders, sends the amount **from the database** (`Math.round(order.total * 100)`), and uses an idempotency key.
- **Webhook:** `yoco-webhook` rejects unsigned requests, enforces a timestamp tolerance, compares `amountInCents` against the DB total, and only then flips `payment_status='paid'`.
- **Return page:** `OrderConfirmation` polls the DB for 30 s after `?payment=success` — it **never trusts the query string** to mark anything paid. Correct.

✅ *Hardened:* a spoofed `?payment=success` URL cannot mark an order paid. Only the signed webhook can.

#### Step 2 — Add rate limiting to order creation (the real P0)

You have no protection at all today. Here is a self-contained Postgres implementation — **it needs no external service.**

1. Create a new file: `supabase/migrations/20261124180000_order_rate_limit.sql`
2. Paste this in:

```sql
-- Per-caller order throttle. Keyed on the phone number (always present) plus
-- the caller IP when the Edge Function forwards it.
create table if not exists public.order_rate_limits (
  bucket_key   text primary key,
  window_start timestamptz not null default now(),
  request_count integer not null default 0
);

alter table public.order_rate_limits enable row level security;
-- No policies: only SECURITY DEFINER functions touch this table.

create or replace function public.check_order_rate_limit(
  p_bucket_key text,
  p_max integer default 5,
  p_window_minutes integer default 60
)
returns void
language plpgsql
security definer
set search_path = ''
as $$
declare
  v_count integer;
  v_start  timestamptz;
begin
  if p_bucket_key is null or btrim(p_bucket_key) = '' then
    return; -- never block a legitimate order because a key is missing
  end if;

  select request_count, window_start
    into v_count, v_start
  from public.order_rate_limits
  where bucket_key = p_bucket_key
  for update;

  if not found then
    insert into public.order_rate_limits (bucket_key, request_count, window_start)
    values (p_bucket_key, 1, now());
    return;
  end if;

  -- Window expired: reset the counter.
  if now() >= v_start + make_interval(mins => p_window_minutes) then
    update public.order_rate_limits
       set request_count = 1, window_start = now()
     where bucket_key = p_bucket_key;
    return;
  end if;

  if v_count >= p_max then
    raise exception 'Too many orders from this number. Please wait a few minutes or WhatsApp Roma.'
      using errcode = '42900'; -- too_many_requests, surfaced as HTTP 429
  end if;

  update public.order_rate_limits
     set request_count = request_count + 1
   where bucket_key = p_bucket_key;
end;
$$;

revoke all on function public.check_order_rate_limit(text, integer, integer) from public, anon, authenticated;
grant execute on function public.check_order_rate_limit(text, integer, integer) to service_role;

-- Housekeeping so the table cannot grow forever.
create or replace function public.prune_order_rate_limits()
returns void
language sql
security definer
set search_path = ''
as $$
  delete from public.order_rate_limits
  where window_start < now() - interval '24 hours';
$$;
```

3. Now call it from the RPC. Open `supabase/migrations/20261124170000_direct_locked_orders_and_receipts.sql` **only to read it** — do not edit an applied migration. Instead, create a new migration `20261124180100_order_rate_limit_hook.sql` that re-creates `place_storefront_order` with one line added. Find this block near the top of the function body:

```sql
  v_clean_name := btrim(coalesce(p_customer_name, ''));

```

and insert immediately **after** it:


4. Also throttle by IP from the Edge Function. Open `supabase/functions/place-direct-order/index.ts` and, immediately **before** the `callerClient.rpc('place_storefront_order', …)` call, add:

```ts
    // Best-effort IP throttle: 20 orders per IP per hour. Never blocks a
    // legitimate order if the header is missing.

      req.headers.get('x-forwarded-for')?.split(',')[0]?.trim() ||
      req.headers.get('x-real-ip')?.trim() ||
```

5. Handle the 429 gracefully in the same file — change the error return to:

#### Step 4 — Validate the phone number properly (10 min)

1. Create `supabase/migrations/20261124180200_phone_format.sql`:
```sql
-- Reject phone numbers that are obviously not phone numbers.
-- Accepts 0721234567, +27 72 123 4567, 27 72 123 4567.
create or replace function public.normalize_sa_phone(p_raw text)
returns text
language plpgsql
immutable
set search_path = ''
as $$
declare
  v_digits text;
begin
  v_digits := regexp_replace(coalesce(p_raw, ''), '[^0-9]', '', 'g');
  if v_digits ~ '^0[1-9][0-9]{8}$' then
    return '27' || substr(v_digits, 2);        -- 0721234567 -> 27721234567
  elsif v_digits ~ '^27[1-9][0-9]{8}$' then
    return v_digits;
  elsif v_digits ~ '^[1-9][0-9]{7,14}$' then
    return v_digits;                            -- international, pass through
  end if;
  return null;
end;
$$;

revoke all on function public.normalize_sa_phone(text) from public, anon, authenticated;
grant execute on function public.normalize_sa_phone(text) to service_role;
```
